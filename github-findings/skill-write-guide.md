# 写技能规范 · TDD 式（借鉴 obra/superpowers）

> 核心信条：**「写技能 = 对流程文档做测试驱动开发。」**
> 「没看过 agent 没有这个技能时怎么失败，就不知道技能教得对不对。」
> 更新：2026-08-03（从 superpowers 移植，26.5万⭐ 经验）

---

## 一、什么时候才写技能（先筛，别滥用）

**应该写**：会被重复使用、有明确"怎么做"的流程、agent 容易做错或偷懒跳过的地方。

**不要写**（这些都不值得技能）：
- 一次性方案
- 别处已有充分文档的标准做法
- 项目特定约定 → 放 instructions 文件（如 AGENTS.md），不是技能
- **机械性约束 → 能用正则/脚本自动强制的，就去自动化，别浪费文档**

---

## 二、TDD 三角色对照

| 软件开发 TDD | 写技能 |
|---|---|
| 测试用例 | 压力场景 + 一个真实子代理任务 |
| 生产代码 | SKILL.md 文档 |
| RED（红） | 没有该技能时，agent 在这场景里**犯规**（先跑 baseline，记录它怎么错） |
| GREEN（绿） | 加了技能后，agent 遵守流程不犯规 |
| Refactor（重构） | 堵新漏洞，同时保持已合规的部分不倒退 |

---

## 三、强制五步流程（skill-workshop 提案前必须过）

1. **跑 baseline**：用一个真实的子代理任务跑一遍，**没有技能时它怎么失败**——记下它的"合理化辩解"（它以为自己做得对的地方）
2. **写最小 SKILL.md**：只针对 baseline 里观察到的**具体违规**，写最小化文档。不写"建议"，写"必须"
3. **验证 GREEN**：再跑同一个子代理任务，确认它遵守了
4. **堵漏洞**：观察还有没有新的犯规方式，补进文档（每轮只修一个违规，勿贪多）
5. **记录"何时不适用"**：明确这个技能解决不了什么，防止 agent 错误套用

---

## 四、技能组织的三分法（metadata 标注）

每个 SKILL.md 明确自己是哪一类，agent 才知道"按步骤做 / 换思路 / 查资料"：

- **type: technique** — 有明确步骤的方法（例：root-cause tracing、分步排查）
- **type: pattern** — 看待问题的思维方式（例：flatten-with-flags、先测不变量）
- **type: reference** — API 文档、语法速查、工具清单（查完就走，不纠结）

---

## 五、写作红线（Anti-patterns）

- ❌ **不写叙事**：技能是"参考手册"，不是"上次我是怎么解决这个问题的故事"
- ❌ **不用模糊词**：把"应该/可能/建议"改为"必须/不允许"（Mandatory workflows, not suggestions）
- ❌ **不写无关背景**：只保留能让 agent 正确执行的指令
- ✅ **每次只教一件事**：一个技能解决一个明确的失败模式
- ✅ **机械约束交给自动化**：能用脚本/正则强制的，别写进文档

---

## 六、落地到 OpenClaw

- 新技能提案（skill_workshop create/update）附上："baseline 失败记录 + GREEN 验证记录"两段
- 提案的 `evidence` 字段就是放这些观察结果的
- 日常维护：agent 在某场景反复犯错 → 这本身就是"该补一个技能"的信号（先跑 baseline 再写）
