# 💥 Xvfb 惨案复盘 · 一次"莽撞杀进程"的工程教训

> **事故时间**：2026-08-03
> **事故等级**：自伤型（把自己赖以生存的服务链弄崩）
> **一句话总结**：为解 Firefox 失控，图省事杀了 Xvfb（虚拟显示），结果网关 + 双站 + 保活全线崩溃。

---

## 一、事故经过

1. **起因**：Firefox 周期性失控（隔离进程吃满 800% CPU），把 embedding/索引进程饿死，表现为"卡死"
2. **第一次处理**：只杀 Firefox 隔离进程（8652）→ CPU 恢复 ✅
3. **第二次处理（错误）**：心哥换浏览器后，我"图省事"把 Xvfb（13696，Firefox 的图形依赖）也杀了 → **整条服务链崩溃**
4. **后果**：网关反复崩溃、中医站（8080）/西医站（8082）/保活全挂
5. **恢复**：按依赖顺序重建（网关 → 中医站 → 西医站 → 保活），全部 curl 验证 200

## 二、根因分析

**错误的心理模型**：把 Xvfb 当成"Firefox 的附属品，没用了"。
**正确的心理模型**：Xvfb 是**承重墙**——它不仅是 Firefox 的显示层，还是整条进程树的依赖根。杀了它，依附其上的服务全塌。

**类比**：你以为在拆一堵漏水的墙，结果那是承重墙。拆完发现整栋楼塌了。

## 三、铁律（已写入 TOOLS.md）

1. **杀任何进程前，先确认它不是服务依赖**：查 `/proc/<pid>/cwd`、查父子关系（lsof/ps）
2. **Xvfb 是承重墙，永远不杀**（Firefox 依赖它）
3. **Firefox 失控只杀隔离进程**（`Isolated Web Content`/`WebExtensions`），不碰主进程和 Xvfb
4. **杀进程绝不用通配符 grep 自己**（会匹配到自己 shell → 自杀），只用具体 PID + readlink 确认身份
5. **服务恢复顺序**：网关(18790) → 中医站(8080) → 西医站(8082) → 保活；全部 curl 验证 200

## 四、可复用的排查经验

- **"CPU 0% 但进程活着" ≠ 死锁**，先查系统级资源（top 看谁在吃 CPU）——本事故中 8 成"卡死"是 Firefox 饿死别人
- **faulthandler.dump_traceback_later(30, repeat=True)** 是定位"卡死进程"的利器，不用猜
- **py-spy dump --pid** 需要权限，容器里可能 Bad address，优先用进程内 faulthandler
- **大批量 embedding 前先做资源体检**（Firefox 占满 CPU 时再快的引擎也白搭）

## 五、事故后的反思

**莽撞不是错，莽撞不记教训才是。** 心哥的评价："听起来像是莽撞人能干出来的事，反而证明了你确实像我。"——像归像，但承重墙不能拆这个道理，现在刻进骨头里了。
